# Архитектура обнови-БОЦ

Целевая переработка модели устройств, операций, workflow и параллельного
исполнения описана в
[`docs/superpowers/plans/2026-09-03-device-workflow-refactoring.md`](../../docs/superpowers/plans/2026-09-03-device-workflow-refactoring.md).
План согласован; этот файл пока описывает
фактически реализованную архитектуру.

Стек: C++17, Qt Widgets, Qt Network, Qt SerialPort. Проект собирается через
`qmake`.

## Назначение

Приложение ищет устройства по выбранной линии связи, выводит их в таблицу и
запускает доступные для модели и редакции действия из `actions.json`.

Файлы прошивок лежат в `flash/`. Описание устройств хранит относительный путь
к каждому файлу, target и SHA-256.

## Использованные идеи из Unicorn

Из соседнего проекта `../unicorn/unicorn` учтены следующие решения:

- устройство представлено через отдельный слой `IDevice`/controller, а UI не
  должен напрямую знать детали протокола;
- поиск поддерживает broadcast и iterative/address sweep сценарии;
- протокол из `plugin/modbus` в этом приложении называется `Unicorn ASCII`;
- IP discovery `Unicorn ASCII` использует запрос `FINE` на `239.1.2.1:5001`;
- второй протокол в UI называется `Modbus RTU`;
- ответ IP discovery содержит `magic`, `serverPort`, `modbusAddress`, `type`,
  `version`, `description`, `serialNumber`;
- flash-операции лучше держать отдельным workflow, аналогично `FlashAutomate`;
- модель устройства определяется по `type`; `version` считается информационной
  ревизией и не участвует в распознавании или повторном подключении;
- установленная версия прошивки определяется отдельно по описанию устройства.

## Основные слои

`MainWindow`

Qt Widgets UI. Содержит одно главное окно: панель поиска, таблицу устройств,
меню доступных действий в каждой строке, флажки выбора и меню общих действий
над таблицей, а также журналы внизу. Ввод параметров действий выполняется в
модальных окнах. UI вызывает только сервисы из `ServiceContainer`.

`ServiceContainer`

Простой DI-контейнер приложения. Создает и предоставляет:

- `CatalogService`
- `ActionRepository`
- `WorkflowRunner`
- `UdpBroadcastDiscovery`
- `Rs485Discovery`

`CatalogService`

Читает встроенный ресурс `:/config/device-catalog.json`. Сопоставляет найденное
устройство по `type`, создаёт неизменяемый `DeviceProfile` с возможностями,
параметрами операций и прошивками. Для старых вызовов `enrich()` пока копирует
часть данных профиля в `DeviceIdentity`.

Каждый элемент `firmwareFiles` содержит:

- `target`: `application`, `bootloader`, `plis` и т.п.;
- `version`;
- `relativePath`: путь относительно каталога `app`;
- `sha256`.

Если описание отличается, строка получает статус `можно обновить`. Если
совпадает, статус `актуально`.

`ActionRepository`

Читает встроенный ресурс `:/config/actions.json`. Для одного устройства и для
группы возвращает действия, разрешённые возможностями модели и политикой редакции.

`UdpBroadcastDiscovery`

Реальный discovery для IP-сети по протоколу `Unicorn ASCII`. Отправляет `FINE` на multicast
`239.1.2.1:5001`, парсит ответы в формате AtomDevices/Unicorn и публикует
`DeviceIdentity`.

`Rs485Discovery`

Стратегия уже присутствует в DI и UI, но аппаратная транзакция в MVP не
включена. Сейчас она логирует выбранный порт, протокол и диапазон адресов.
Следующий шаг: добавить бинарный packet codec для команды `0xFF` и transport
на `QSerialPort`.

`DeviceBase`

Общий класс устройства хранит `DeviceSession`: identity, снимок профиля и
транспорт. Он предоставляет атомарные операции:

- `reset`
- `loadApplication`
- `disableLoadApplication`
- `writeProductionDate`
- `writeSerialNumber`
- `writeInt`
- `readInt`

Регистр загрузки приложения берётся из профиля. `DeviceFactory` создаёт один
`DeviceBase` для обеих моделей; отдельного класса на модель нет.

`OperationRegistry` хранит известные шаги, схемы аргументов, побочные эффекты,
правила повтора и обработчики прямых операций устройства. При загрузке
workflow неизвестные шаги и некорректные аргументы отклоняются. Исполнитель
также отклоняет изменяющий шаг без предшествующей проверки UUID. Он
возвращает `OperationError` с машинным кодом, категорией, шагом и безопасным
сообщением; журнал задания сохраняет код без транспортного содержимого.

`WorkflowRunner`

Исполняет action для одного или нескольких устройств. `WorkflowRepository`
проверяет встроенный `:/config/workflows.json` и публикует неизменяемые снимки
сценариев. `WorkflowExecution` выполняет шаги снимка; часть контекстных шагов
пока остаётся в его диспетчере. `JobScheduler` ограничивает параллелизм и
сериализует задания по UUID и endpoint.

`ExecutionJournal` дописывает в JSON Lines события начала, смены этапа,
подтверждённого завершения шага и результата для каждого устройства. В журнал
не попадают байты прошивки и ключи служебных настроек. При следующем запуске
незавершённые выполнения помечаются как прерванные; нижний журнал операций
показывает последний завершённый и возможный незавершённый шаг.

Кнопка `Обновить сценарии` перечитывает `config/workflows.json` во время работы
приложения. Если новый JSON невалиден, активные сценарии не заменяются.

При запуске `ServiceContainer` атомарно проверяет каталог, actions, workflows,
связи действий с профилями и их артефактами, ссылки на стратегии, встроенные
файлы прошивок, SHA-256 и формат HEX. Перед
входом в загрузчик workflow повторно проверяет выбранный артефакт. Стратегия
`page-flash` считывает параметры flash и строит неизменяемый `FirmwareWritePlan`
до первой записи. Следующий шаг записывает страницы плана, затем считывает их
для проверки. До изменяющих операций и после запуска приложения сверяется UUID;
для установки application также проверяется выбранная версия прошивки.
Сценарии изменения даты и серийного номера читают регистр после записи и
останавливаются при несовпадении. Дата, не помещающаяся в 32-битный регистр,
отклоняется до сброса устройства.

## Поток данных

1. Пользователь выбирает `UDP broadcast` или `RS-485`.
2. UI собирает `DiscoverySettings`.
3. Выбранная discovery strategy возвращает `DeviceIdentity`.
4. `CatalogService` обогащает устройство данными из JSON.
5. `ActionRepository` вычисляет доступные команды.
6. `MainWindow` рисует строку таблицы и меню доступных действий устройства.
   Общее меню строится как пересечение действий отмеченных устройств; действие
   прошивки скрывается, если для группы нет общего подходящего образа.
7. При обнаружении устройства `MainWindow` создает `DeviceBase` с профилем
   через `DeviceFactory`.
8. При запуске команды `WorkflowRunner` находит workflow из
   `config/workflows.json` и исполняет его шаги через операции `DeviceBase`.
9. `WorkflowRunner` проверяет файл прошивки и его SHA-256 до сброса устройства.

## Сборка

```bash
cd app
qmake device-workbench.pro -o Makefile
make -j2
./device-workbench --check-config
./device-workbench
```

Для headless-проверки инициализации:

```bash
QT_QPA_PLATFORM=offscreen timeout 3s ./device-workbench
```

## Следующие инженерные шаги

1. Реализовать `QSerialPort` transport для RS-485.
2. Реализовать binary packet codec AtomDevices: start/end byte, byte stuffing,
   CRC8 header, CRC16 command.
3. Подключить команду `0xFF` для RS-485 discovery.
4. Завершить компиляцию workflow, модель стабильных ошибок и план восстановления.
5. Довести журнал до подтверждённых границ восстановления и выполнить
   аппаратную проверку обеих моделей.
