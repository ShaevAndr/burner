# План рефакторинга модели устройств и workflow

Статус: черновик для согласования.

Назначение: заменить наследование по модели устройства композицией из профиля,
транспорта и узких стратегий; сделать добавление устройств и пользовательских
действий преимущественно декларативным, а выполнение опасных операций — заранее
проверяемым, наблюдаемым и восстанавливаемым.

## 1. Цель и критерии результата

После рефакторинга система должна обеспечивать следующее:

1. Новая модель на существующем протоколе и с существующими атомарными
   операциями добавляется изменением и проверкой конфигурации без нового класса
   устройства.
2. Новое пользовательское действие из существующих операций добавляется через
   `actions.json` и `workflows.json` без изменения исполнителя.
3. Новая атомарная операция требует одного типизированного C++-обработчика,
   регистрации контракта и тестов, но не изменения цепочки `if/else` в runner.
4. Новый протокол или принципиально новый алгоритм добавляется узкой стратегией,
   а не наследником со всем поведением конкретной модели.
5. Все конфигурации, ссылки на операции, аргументы, firmware-артефакты и
   обязательные пути восстановления проверяются до показа действия в UI.
6. Ни один изменяющий устройство шаг не начинается до завершения доступного
   офлайн-preflight.
7. Для одного физического устройства одновременно выполняется не более одной
   изменяющей операции. Разные устройства могут выполняться параллельно в
   контролируемом пуле.
8. Ошибка должна иметь стабильный код, этап, признак повторяемости и безопасное
   описание для оператора. Успешный результат должен подтверждаться чтением
   устройства, а не только отсутствием транспортной ошибки.

## 2. Зафиксированные решения

### 2.1. Не создавать класс на каждую модель

Отдельный C++-класс модели не является основной точкой расширения. Текущий
`BocV12Device` переопределяет `disableLoadApplication`, но выполняет ту же запись
`int[0] = 0`, что и `DeviceBase`; это различие должно быть параметром профиля.

Новый класс или стратегия допускаются только когда меняется алгоритм:

- формат или протокол обмена;
- способ входа в bootloader;
- алгоритм записи или проверки flash;
- кодирование специфичных данных;
- обязательная аппаратная последовательность, которую нельзя безопасно выразить
  параметрами существующей операции.

Даже в этих случаях должен добавляться узкий интерфейс (`ITransport`,
`IBootloaderEntryStrategy`, `IFirmwareFlashStrategy`), а не наследник, владеющий
всем поведением устройства.

### 2.2. JSON остаётся декларативным и не исполняет произвольный код

JSON может выбирать только операции и стратегии, зарегистрированные в C++.
Каждая операция имеет типизированный контракт аргументов, допустимые состояния,
классификацию побочного эффекта и правила повтора. Неизвестный `op` является
ошибкой загрузки конфигурации, а не ошибкой в середине выполнения.

### 2.3. Workflow сначала компилируется, потом исполняется

`WorkflowRepository` должен возвращать не сырой список строковых шагов, а
неизменяемый `CompiledWorkflow`. Компиляция разрешает ссылки на операции,
проверяет аргументы и строит план восстановления. Исполнитель не должен содержать
список имён операций и длинный диспетчер `if/else`.

### 2.4. Параллелизм принадлежит scheduler, а не workflow

Workflow описывает последовательность одного устройства. `JobScheduler`
управляет очередью, блокировкой устройства и параллельной обработкой группы.
Операции и JSON не создают потоки самостоятельно.

### 2.5. Поставка остаётся модульным монолитом

Новые компоненты остаются внутри одного Qt-приложения. Динамические плагины и
отдельный backend не вводятся: они увеличили бы поверхность отказа и сложность
поставки без текущей необходимости.

## 3. Целевая модель

```text
DeviceCatalog JSON
        |
        v
DeviceProfile ---- StrategyRegistry
        |                  |
        +---- DeviceSession+---- IDeviceTransport
                    |
Action JSON -> WorkflowCompiler <- OperationRegistry
                    |
             CompiledWorkflow
                    |
               JobScheduler
                    |
             WorkflowExecutor
                    |
          ExecutionJournal / UI
```

### 3.1. `DeviceIdentity`

Содержит только данные, полученные от конкретного экземпляра устройства:
endpoint, UUID, serial number, type, version, description, текущее состояние и
обнаруженную версию firmware. Он не должен владеть каталогом прошивок,
capabilities или параметрами регистров.

### 3.2. `DeviceProfile`

Неизменяемое описание известной модели из каталога:

- стабильный `id`;
- правила сопоставления application и bootloader identity;
- protocol/transport requirements;
- capabilities;
- именованные параметры операций, включая номера регистров;
- выбранные стратегии;
- каталог firmware и разрешённые переходы.

В конфигурации следует использовать именованные параметры, например
`applicationLoadRegister`, а не зашивать `int[0]` в класс устройства.

### 3.3. `DeviceSession`

Связывает один runtime-экземпляр:

```text
DeviceSession
  identity: DeviceIdentity
  profile: shared immutable DeviceProfile
  transport: IDeviceTransport
  state: discovered | application | bootloader | busy | unavailable
```

`DeviceSession` предоставляет согласованный снимок identity и является ключом
блокировки scheduler. Предпочтительный физический ключ — UUID; до получения UUID
используется endpoint с обязательной повторной сверкой UUID перед изменением.

### 3.4. `OperationRegistry`

Реестр атомарных операций должен хранить для каждого `operationId`:

```text
id
argumentSchema
allowedDeviceStates
requiredCapabilities
sideEffect: none | reversible | destructive
idempotency: safe | conditional | unsafe
defaultTimeout
retryPolicy
handler
```

Базовый набор:

- `device.ensureUuid`;
- `device.reset`;
- `device.enterBootloader`;
- `device.loadApplication`;
- `device.waitForIdentity`;
- `register.read`;
- `register.write`;
- `firmware.validateTransition`;
- `firmware.loadArtifact`;
- `flash.readParameters`;
- `flash.buildPagePlan`;
- `flash.writePages`;
- `flash.verifyPages`;
- `firmware.verifyInstalledVersion`.

Доменные операции могут использовать transport, profile и execution context,
но не должны обращаться к UI.

### 3.5. Узкие стратегии

Стратегии регистрируются статически при сборке:

```text
IDeviceTransport
  UnicornAsciiTransport
  ModbusRtuTransport
  FakeTransport

IBootloaderEntryStrategy
  ResetAndRediscover
  VendorCommandAndRediscover

IFirmwareFlashStrategy
  PageFlashStrategy
  BlockFlashStrategy
  TestNoWriteStrategy
```

Профиль ссылается на стратегию по стабильному ID. Отсутствующая стратегия
должна отклонять профиль при запуске приложения.

### 3.6. `WorkflowCompiler`

Компилятор должен проверить:

- уникальность action и workflow ID;
- существование каждой операции и стратегии;
- типы, обязательность и диапазоны аргументов;
- соответствие required capabilities профилю;
- допустимость начальных и конечных состояний;
- положительные и ограниченные timeout/retry;
- наличие recovery для workflow, оставляющего устройство в bootloader;
- существование firmware-файла, его SHA-256 и непустое содержимое;
- допустимость переходов firmware;
- запрет custom firmware в external edition;
- отсутствие изменяющего шага до обязательного офлайн-preflight.

Результатом является `CompiledWorkflow`, содержащий ссылки на обработчики и
проверенные аргументы. Активная конфигурация заменяется только целиком и только
после успешной компиляции. Активное задание продолжает использовать снимок
старого плана.

### 3.7. `JobScheduler` и `WorkflowExecutor`

`JobScheduler` должен:

- принимать одно пользовательское задание для одного или нескольких устройств;
- создавать отдельный последовательный execution для каждого устройства;
- запрещать конкурентные записи в одно физическое устройство;
- запускать разные устройства в ограниченном пуле;
- агрегировать прогресс, не смешивая ошибки устройств;
- поддерживать кооперативную отмену только в безопасных точках;
- выдавать каждому заданию `jobId`, а каждому устройству `executionId`.

`WorkflowExecutor` исполняет один `CompiledWorkflow` для одного `DeviceSession`.
Он не создаёт потоки и не выбирает действия UI.

## 4. Инварианты надёжности

1. Любая запись требует подтверждённого UUID. Несовпадение UUID после reset или
   rediscovery завершает операцию до записи.
2. Firmware-файл, SHA-256, формат Intel HEX и статические диапазоны должны быть
   проверены до reset устройства.
3. Параметры flash, доступные только из bootloader, проверяются после входа в
   bootloader, но до первой записи страницы.
4. План страниц строится полностью до первой записи. Запись не должна попутно
   обнаруживать новую ошибку формата файла.
5. Записанная страница считается успешной только после положительного ответа.
   Вся прошивка считается успешной только после обратного чтения всех страниц и
   проверки запущенной версии application.
6. Автоматический retry разрешён только для операции, чей контракт явно
   обозначает безопасную повторяемость. Проверка подстроки в тексте ошибки не
   должна определять retry.
7. Ошибка после входа в bootloader запускает явно заданный recovery. Результат
   recovery фиксируется отдельно и не превращает исходную ошибку в успех.
8. Отмена после первой записи страницы должна завершаться контролируемым
   состоянием `interrupted`; приложение не должно сообщать, что старая или новая
   прошивка гарантированно работоспособна.
9. Reload конфигурации не меняет уже запущенный execution plan.
10. Неизвестная модель или capability запрещает опасное действие по принципу
    deny-by-default.

## 5. Целевой процесс прошивки application

### Фаза A: офлайн-preflight без изменения устройства

1. Зафиксировать UUID, identity, profile, action inputs и версии конфигурации.
2. Проверить разрешение edition и capability.
3. Проверить переход текущей firmware к выбранной.
4. Разрешить путь firmware только через доверенный repository.
5. Прочитать файл, проверить SHA-256 и разобрать Intel HEX.
6. Проверить обязательные metadata и статически известные диапазоны.
7. Сформировать неизменяемую часть `FirmwareWritePlan`.

### Фаза B: device-preflight без записи flash

1. Повторно прочитать UUID.
2. Выполнить reset и обнаружить bootloader.
3. Сверить UUID, bootloader identity и профиль.
4. Прочитать параметры flash.
5. Проверить, что образ помещается в выбранную область.
6. Построить полный список номеров страниц и ожидаемых байтов.
7. Запретить автоматическую загрузку application непосредственно перед записью.

Если bootloader требует раннего запрета автозапуска, это оформляется свойством
`IBootloaderEntryStrategy`, а не неявным изменением порядка в общем workflow.

### Фаза C: изменение устройства

1. Записать страницы в детерминированном порядке.
2. После каждой страницы зафиксировать результат в execution journal.
3. Прочитать записанные страницы и сравнить каждый байт.
4. Загрузить application.
5. Дождаться устройства и сверить UUID, application identity и целевую firmware.
6. Обновить `DeviceSession` и завершить execution как `succeeded`.

## 6. Состояния задания

```text
queued
  -> validating
  -> waitingForDevice
  -> preparingDevice
  -> writing
  -> verifyingFlash
  -> startingApplication
  -> verifyingApplication
  -> succeeded

Из любого выполняемого состояния:
  -> failed
  -> recovering -> failedRecovered | failedRecovery
  -> cancelling -> cancelled | interrupted
```

`succeeded` является терминальным только после проверки application. Закрытие UI,
падение процесса или потеря связи не должны создавать ложный успех.

## 7. Модель ошибок

Ввести `OperationError`:

```text
code: стабильный машинный код
category: configuration | policy | identity | transport | protocol | device | verification | cancelled
operationId
deviceId / UUID
retryable
safeMessage
technicalDetails
rawTransportData (только для технического журнала)
```

Минимальные стабильные коды:

- `CONFIG_UNKNOWN_OPERATION`;
- `CONFIG_INVALID_ARGUMENT`;
- `POLICY_ACTION_DENIED`;
- `POLICY_TRANSITION_DENIED`;
- `IDENTITY_UUID_MISMATCH`;
- `DEVICE_BOOTLOADER_NOT_FOUND`;
- `TRANSPORT_TIMEOUT`;
- `PROTOCOL_INVALID_RESPONSE`;
- `FIRMWARE_HASH_MISMATCH`;
- `FIRMWARE_INVALID_FORMAT`;
- `FIRMWARE_OUT_OF_RANGE`;
- `FLASH_WRITE_FAILED`;
- `FLASH_VERIFY_MISMATCH`;
- `APPLICATION_VERSION_MISMATCH`;
- `OPERATION_CANCELLED`;
- `RECOVERY_FAILED`.

UI показывает `safeMessage`, а журнал сохраняет код, этап и технические детали.

## 9. Стратегия тестирования

| Риск | Проверка | Уровень | Ожидаемый результат |
|---|---|---|---|
| Неизвестный `op` | Загрузить workflow с незарегистрированным ID | Unit | Конфигурация отклонена до UI |
| Неверный аргумент | Передать строку вместо номера регистра | Unit | Стабильная ошибка schema |
| Подмена устройства | Изменить UUID после reset | Integration/fake transport | Запись не начинается |
| Повреждённый файл | Изменить байт firmware | Unit | `FIRMWARE_HASH_MISMATCH` до reset |
| Выход за flash | Вернуть меньший размер flash | Integration | Ноль записанных страниц |
| Частичная запись | Ошибка на странице N | Integration | `FLASH_WRITE_FAILED`, recovery зафиксирован |
| Повреждение записи | Вернуть отличающийся байт | Integration | `FLASH_VERIFY_MISMATCH` |
| Потеря application | Не отвечать после load command | Integration | Ошибка, а не ложный успех |
| Гонка | Запустить два задания на один UUID | Concurrency | Второе ожидает или отклонено |
| Группа устройств | Одно успешно, одно с timeout | Integration | Два независимых результата |
| Отмена | Отменить до и после начала записи | Integration | `cancelled` или `interrupted` по правилам |
| Reload | Перезагрузить config во время задания | Integration | Активен старый immutable plan |
| External edition | Подать запрещённый action напрямую | Unit/integration | Deny независимо от UI |

Fake transport должен поддерживать сценарное программирование ответов, timeout,
смену endpoint, смену UUID, ошибки конкретной страницы и повреждение read-back.
Отдельные контрактные тесты должны проверять реальные пакеты
`UnicornAsciiTransport` без оборудования. Hardware smoke test остаётся отдельным
релизным шагом и не заменяет автоматические тесты.

## 10. Поставка и откат

Рефакторинг выполняется по этапам, при этом рабочая ветка после каждого этапа
должна собирать обе редакции и проходить старые сценарии. Не следует одновременно
менять transport wire format, UI и workflow engine.

Порядок включения:

1. Добавить новые модели рядом со старыми и покрыть адаптерами.
2. Перевести существующие действия на compiled workflow за feature flag сборки.
3. Сравнить результаты старого и нового планировщика на fake transport.
4. Выполнить hardware smoke test на БОЦ-В-6 и БОЦ-В-12.
5. Включить новый путь по умолчанию.
6. Удалить `DeviceBase::operations`, `BocV12Device` и старый dispatcher только
   после успешной проверки обеих редакций.

Откат до удаления старого пути выполняется возвратом build-time feature flag.
После удаления старого пути откат выполняется установкой предыдущего релиза;
конфигурация и firmware остаются встроенными в соответствующий EXE.

## 11. Открытые вопросы

1. **Лимит параллельных устройств.** Рекомендуется сделать его конфигурационным и
   до аппаратного нагрузочного теста использовать консервативное значение.
   Требуется определить безопасный предел для сети и устройств.
2. **Отмена после начала flash.** Рекомендуется разрешать немедленную отмену до
   первой записи, а после неё — только на границе страницы с результатом
   `interrupted`. Нужно подтвердить требования оператора.
3. **Формат execution journal.** Для текущего desktop-приложения рекомендуется
   append-only JSON Lines с атомарной записью отдельных событий; SQLite стоит
   рассматривать только при появлении истории, фильтрации и повторного запуска
   заданий из UI.
4. **Подпись firmware.** SHA-256 защищает от случайного повреждения, но не
   подтверждает издателя. Если firmware может поступать вне доверенной сборки,
   потребуется цифровая подпись и управление публичными ключами.
5. **Горячая перезагрузка workflow.** Для production-релиза рекомендуется
   разрешать только атомарную замену полностью проверенного набора и запрещать
   reload во время активной операции либо сохранять snapshot старой версии.
6. **Совместимость протоколов.** Нужно подтвердить, являются ли различия будущих
   моделей только параметрами Unicorn ASCII или ожидаются модели с иным набором
   команд и форматом flash.

Ни один открытый вопрос не блокирует этапы 0–4. Лимит параллелизма и семантика
отмены должны быть подтверждены до завершения этапа 6; формат журнала — до этапа
7; требования к подписи firmware — до разрешения внешних файлов в production.
