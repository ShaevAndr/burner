# Device Workbench MVP

Статус: черновик для согласования.

## Цель

Первая версия должна дать оператору прозрачный инструмент для поиска устройств,
просмотра найденных приборов и запуска простых одиночных или групповых действий:
обновить прошивку, перезагрузить, прочитать параметры или телеметрию.

MVP не должен смешивать все линии связи в один поиск. Пользователь должен явно
выбрать режим поиска в одном `select`: UDP broadcast или RS-485 address sweep.

## Подтвержденные требования

1. Приложение должно иметь пользовательский UI.
2. Поиск должен быть разделен на UDP broadcast и RS-485.
3. TCP-сценарий первой версии должен использовать существующий UDP
   broadcast-механизм протокола:
   отправить команду запроса типа и описания устройства и принять готовые ответы.
4. RS-485-поиск должен быть отдельным сценарием по выбранной линии и диапазону
   адресов.
5. Самописный протокол должен быть реализован как стратегия протокола.
6. Modbus RTU и будущие протоколы должны добавляться через тот же контракт
   стратегии.
7. Зависимости должны подключаться через DI, чтобы транспорт, протоколы,
   workflow и UI не создавали друг друга напрямую.
8. В каждой строке устройства должен быть список возможных действий для этого
   устройства.
9. При массовом выделении галочками сверху должно быть меню общих действий,
   доступных для всей выбранной группы.
10. Левое меню в первой версии сохраняется.
11. Предпочтительные языки команды: C++, Python, TypeScript/React. Qt 5.12
    допустим к рассмотрению.

## Термины

- Транспорт: низкоуровневый канал передачи байтов, например TCP, UDP broadcast
  или serial port для RS-485.
- Протокол: кодирование команд, парсинг ответов, CRC, escaping, обработка
  ошибок и доменные команды устройства.
- Стратегия протокола: реализация единого интерфейса для конкретного протокола.
- Устройство: найденный прибор с transport endpoint, protocol id, type, version,
  description и capabilities.
- Catalog: JSON-документ известных типов приборов, прошивок и возможностей.
- Action: JSON-описание пользовательского действия и workflow шагов.
- Workflow: последовательность шагов обслуживания выбранных устройств.

## MVP UI

Левое меню:

- Обнаружение
- Прошивки

Область поиска должна содержать один `select` линии связи:

- UDP broadcast
- RS-485

После выбора линии UI должен показывать только настройки выбранной линии,
выбор протокола и соответствующую кнопку поиска.

Для UDP broadcast в первой версии достаточно:

- сетевой интерфейс;
- протокол;
- кнопка "Broadcast поиск";
- журнал отправки запроса типа и описания;
- таблица полученных ответов.

Для RS-485 в первой версии достаточно:

- serial port;
- baud rate;
- frame format;
- протокол;
- адрес старта поиска;
- адрес конца поиска;
- тайм-аут ответа;
- кнопка "Поиск RS-485".

Таблица устройств должна показывать:

- checkbox выбора;
- имя устройства;
- линия связи;
- адрес или endpoint;
- тип, полученный из ответа устройства;
- версию, полученную из ответа устройства;
- короткое описание, полученное из ответа устройства;
- статус совместимости;
- иконки действий для строки с подсказками.

Таблица должна показывать только устройства, найденные через текущий выбранный
интерфейс и текущий выбранный протокол. Переключение линии или протокола должно
очищать или заменять список текущего поиска, чтобы оператор не смешивал приборы
из разных контекстов.

Меню массовых действий должно находиться прямо над таблицей и показывать
только пересечение действий, доступных для всех выбранных устройств. Если
пересечение пустое, меню должно быть неактивно или показывать безопасное
объяснение.

В MVP доступны только две пользовательские команды:

- `flash.application.write`;
- `flash.bootloader.write`.

Эти две команды должны отображаться у каждого найденного устройства и в меню
массовых действий, если выбранные устройства поддерживают соответствующую
capability. Другие действия, включая сброс, чтение профиля и экспорт
телеметрии, в MVP UI не выводятся.

Правый сайдбар в MVP не используется.

При сопоставлении найденного устройства с JSON-каталогом приложение должно
сравнивать `type` и короткое `description` из ответа устройства с настройками
каталога. Если `type` найден, но описание отличается от `expectedDescription`
в JSON, строка должна получить статус "можно обновить". Это означает, что для
устройства рекомендована операция записи flash по правилам каталога. Если
описание совпадает, строка получает статус "актуально". Команды
`flash.application.write` и `flash.bootloader.write` при этом остаются
доступными у всех известных устройств с соответствующими capabilities. Если
`type` не найден в каталоге, устройство отображается как неизвестное и не
получает опасных действий.

## Простая архитектура

```text
UI
  -> Application services
      -> Discovery services
      -> Workflow runner
      -> Catalog service
      -> Action policy service
  -> Ports / interfaces
      -> Transport
      -> ProtocolStrategy
      -> FirmwareRepository
      -> JobRepository
```

В первой версии приложение может быть модульным монолитом. Отдельный backend
процесс нужен только если UI выбран как React в браузерном WebView или отдельном
клиенте.

## Основные интерфейсы

```text
ITransport
  open()
  close()
  send(bytes)
  receive(timeout)

IDiscoveryService
  discover(request) -> Device[]

IProtocolStrategy
  id
  readIdentity(channel, addressOrEndpoint) -> DeviceIdentity
  readProfile(device) -> DeviceProfile
  executeCommand(device, command) -> CommandResult

IActionPolicy
  getAvailableActions(device | device[]) -> Action[]

IWorkflowRunner
  run(action, devices, inputs) -> Job

DeviceBase
  readIdentity()
  getFlashWorkflow(target) -> FlashWorkflow
  prepareFlashWrite(target, artifact)
  writeFlash(target, artifact, progress)
  verifyFlash(target, artifact)
  afterFlashWrite(target)
```

Для UDP broadcast может быть отдельный транспорт или discovery-сервис:

```text
UdpBroadcastDiscovery
  использует AtomDevProtocol.readIdentityBroadcast()
```

В коде транспорт первой версии должен называться по фактической реализации:
`UdpBroadcastTransport` или аналогично. В UI допустимо использовать текст,
понятный оператору, но в текущем макете выбран термин `UDP broadcast`.

## Модель устройств и flash workflow

Для поддержки разных приборов без разрастания условий приложение должно иметь
базовый класс устройства. Базовый класс задает общий контракт записи flash и
общую последовательность шагов, а конкретный класс устройства переопределяет
детали: адреса разделов, размер страницы, подготовку, проверку, задержки,
повторное обнаружение и ограничения.

```text
DeviceBase
  Ad042Device
  Ad052Device
  Ad021Device
  Ad110Device
  GenericModbusIo16Device
```

Команды `flash.application.write` и `flash.bootloader.write` могут использовать
один и тот же workflow id, например `flash.write`, но workflow должен
исполняться через конкретный класс устройства. Это позволяет оставить общую
схему шагов одинаковой, но сделать реализацию специфичной для типа прибора.

Базовая последовательность `flash.write`:

1. Заблокировать устройство на время операции.
2. Повторно прочитать identity и сверить `type`, `version`, `description`.
3. Выбрать target: `application` или `bootloader`.
4. Получить device-specific параметры записи flash.
5. Записать страницы прошивки.
6. Проверить запись, если это включено входным параметром.
7. Выполнить device-specific завершающий шаг.
8. Обновить строку таблицы после повторного обнаружения или повторного чтения
   identity.

## Протокол AtomDevices

Минимальный MVP для самописного протокола:

1. Запрос типа и версии устройства: `0xFF`.
2. Команда `flash.application.write`.
3. Команда `flash.bootloader.write`.

Внутри flash workflow конкретный класс устройства может использовать
низкоуровневые команды протокола, необходимые для записи и проверки flash.
UI и action layer при этом знают только две команды MVP.

## Discovery Flow

### UDP broadcast

1. Пользователь выбирает в `select` линию "UDP broadcast".
2. Пользователь выбирает сетевой интерфейс и профиль протокола.
3. Приложение отправляет broadcast-запрос идентификации.
4. Приложение собирает ответы до истечения окна ожидания.
5. Каждый ответ парсится выбранной стратегией протокола.
6. Найденные устройства добавляются в таблицу.
7. Для известных типов выполняется сопоставление с Catalog.
8. UI показывает доступные действия.

### RS-485

1. Пользователь выбирает в `select` линию "RS-485".
2. Пользователь выбирает порт, скорость, формат кадра и диапазон адресов.
3. Приложение последовательно опрашивает адреса.
4. Для каждого адреса отправляется `0xFF` или аналогичная команда стратегии.
5. Тайм-аут означает "устройства нет" и не считается ошибкой задания.
6. Валидный ответ добавляет устройство в таблицу.
7. Ошибка CRC или ошибка протокола фиксируется в журнале поиска.

## JSON catalog и actions

Catalog должен отвечать на вопрос: "что это за прибор и какая прошивка для него
актуальна".

Actions должны отвечать на вопрос: "что можно сделать с текущим выбором
устройств".

В MVP `actions.example.json` должен содержать только:

- `flash.application.write`;
- `flash.bootloader.write`.

Обе команды могут ссылаться на один workflow `flash.write`; конкретика
исполнения берется из класса устройства, указанного в каталоге через
`deviceClass`.

В первой версии достаточно текущих файлов:

- `device-catalog.example.json`
- `actions.example.json`

Позже их стоит разделить на:

- `catalog/devices/*.json`
- `catalog/firmware/*.json`
- `catalog/actions/*.json`

## Технологический выбор

### Рекомендация для MVP

Рекомендуемый путь: C++ / Qt 5.12 Widgets для desktop UI и низкоуровневой работы
с TCP/serial, без React в первой версии.

Причина: команда знает C++, Qt дает готовые QTcpSocket, QUdpSocket,
QSerialPort, модель таблиц, диалоги, настройки и упаковку desktop-приложения.
Для MVP это меньше движущихся частей, чем связка C++ backend + React frontend.

### Когда брать React + TypeScript

React + TypeScript имеет смысл, если UI будет быстро усложняться: фильтры,
таблицы, прогресс групповых заданий, редакторы JSON, графики телеметрии,
темизация и удаленный web-доступ.

В этом случае backend лучше делать отдельно:

- C++ core service + React UI через WebSocket/HTTP;
- либо Python service + React UI;
- либо Tauri/Wails-подобная оболочка, если C++ не обязателен.

### Qt 5.12

Qt 5.12 удобен для такого MVP, если выбрать Qt Widgets. Он достаточно хорошо
закрывает serial/TCP и обычный desktop UI.

Ограничения:

- версия устаревшая, поэтому новые UI-компоненты и WebEngine-сценарии будут
  менее комфортны;
- React внутри Qt 5.12 через QWebEngine усложнит сборку и отладку;
- если нужен современный web UI, лучше не смешивать его глубоко с Qt Widgets.

## Риски и решения

1. Групповое обновление прошивки опасно. В MVP оно должно иметь preflight,
   подтверждение, журнал и запрет параллельного доступа к одному устройству.
2. RS-485 медленный и полудуплексный. Поиск должен быть последовательным,
   с настраиваемыми тайм-аутами и без агрессивного параллелизма.
3. Broadcast может вернуть дубли. Устройство должно дедуплицироваться по UUID,
   endpoint или стабильной комбинации protocol/type/address.
4. Неизвестное устройство должно отображаться в UI, но получать только базовые
   безопасные действия.
5. JSON actions не должен давать UI право выполнять действие без проверки
   backend policy.

## Этапы реализации

1. Каркас приложения, DI, модели Device/Action/Job.
2. UDP broadcast discovery для AtomDevices `0xFF`.
3. Таблица найденных устройств и две быстрые flash-команды.
4. RS-485 discovery по диапазону адресов.
5. Catalog matching и вычисление доступных действий.
6. Базовый `DeviceBase` и конкретные классы устройств.
7. Job runner для `flash.application.write`.
8. Job runner для `flash.bootloader.write`.
